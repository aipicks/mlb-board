## Core architecture (carry over as-is)

- `build.py` reads everything from `data/*.json` and writes a single static `index.html`. No client-side fetching — all data is baked in at build time.
- Data files, roughly one per concern (adapt names/schemas for NFL):
  - `schedule.json` — this week's games: kickoff time (UTC), teams, starting QBs (or key injury-report designations), team records.
  - `team_season.json` / `team_last_N.json` — rolling team performance (NFL equivalent of MLB's "last-15 games": maybe last-4-games trends, since NFL seasons are short).
  - `player_season.json` — season stats for the players who matter most for the board (QBs at minimum; maybe top skill players).
  - `boxscore_cache.json` — a permanent cache of past game box scores, keyed by game ID, so you never re-fetch a completed game's stats twice.
  - `hist_schedule_N.json` — one archived file per completed week, feeding the rolling stats.
  - `odds.json` — spread/moneyline/total, read from screenshots I paste in (see below).
  - `injuries.json` / `weather.json` (if applicable — outdoor stadiums, cold-weather games) — reset to `[]` when I don't provide anything new; never carry stale data forward silently.
- Static reference data hardcoded in `build.py` itself (like MLB's ballpark factors): things like [stadium type/dome, home-field advantage adjustments] that almost never change — no fetching needed.

## Daily/weekly workflow (the runbook)

When I say "run the board for week N" or "update the board":

1. **Confirm the previous week is fully complete** before archiving it — check every game's final status via [your NFL data source] before treating any score as final. Never fabricate or guess a score.
2. **Archive the completed week** into a new `hist_schedule_N.json`, then bump whatever loop/range in `build.py` includes it in the rolling stats.
3. **Fetch the new week's schedule** — teams, kickoff times (get the exact UTC timestamps right — this matters a lot later for odds matching), starting QBs. If a starter is genuinely unconfirmed (backup competition, injury designation not yet resolved), leave it TBD rather than guessing — don't trust a single secondary source (an odds site, a beat writer tweet) without cross-verification against an authoritative source (official injury report / depth chart).
4. **Fetch season stats** for the relevant players, batched efficiently if the API supports it.
5. **Fetch/verify game logs** for cumulative stats — watch for API truncation (some stats endpoints silently cap results; always sanity-check the returned count against a known total like games played, and re-fetch if it looks short).
6. **Update rolling team/player stats** (last-N-games equivalents) only for teams that actually played since the last update — don't recompute everything from scratch every time, and don't use a "current roster" shortcut for anything that depends on who was actually on the field in past games.
7. **Odds screenshots**: I'll paste in screenshots of a sportsbook's odds board (spread, moneyline, total — and whatever else it shows). Extract every field per game with **pixel-level care**: crop and zoom each row before reading it, don't do a single holistic read of the whole image. Match each game to the schedule by exact kickoff timestamp, not just team names — if two games could plausibly share a matching key (a flex-scheduled doubleheader-equivalent, or a bye-week quirk), guard against one game's odds silently bleeding into another. If I only send screenshots for some of the week's games, that's fine — leave the rest as "odds unavailable," don't reuse stale numbers from a prior week.
8. **Rebuild**: run `build.py`, and treat its own sanity-check output as a gate, not a formality — game count, any hardcoded spot-check values, and (critically) a check that counts how many games are showing "odds unavailable" so a silent matching bug can't slip through unnoticed.
9. **Publish and VERIFY — this is the part I care about most:**
   - After writing files to the published/synced folder, don't just trust that the write call reported success. Read the files back from that location and confirm the actual content and timestamp before telling me anything is done.
   - I would rather you take an extra minute to verify than hand me a status update that turns out to be wrong. Never say something was "built," "saved," or "published" unless you've independently confirmed it.
   - If a git commit hits a sync-related lock error (this happens with OneDrive-synced git folders), don't loop retrying blindly — clear the stale lock if you're able to, retry once, and verify the result via `git log` rather than assuming success or failure from the error text alone. If pushing to GitHub isn't possible from your environment, tell me exactly what command to run and where.

## Hard rules (non-negotiable)

- Never fabricate a score, stat, injury status, odds line, or player identity. Missing data is left blank/omitted, never guessed.
- Never assume a name-to-player match without verifying identity/current team against an authoritative source — this has caught real errors before (a stale news article naming the wrong starter, which didn't match the player's actual current team).
- Cross-check every timestamp-based match (odds to schedule, archived games to team stats) exactly — don't rely on team names alone when two games could collide.
- When I report something looks wrong, don't just re-check your own stored file — re-fetch fresh from the source and compare directly, since the bug might be in what was originally fetched.
- Batch API calls where the source supports it; don't burn calls fetching things one-by-one if a bulk endpoint exists. Don't recompute data for entities that haven't changed since the last run.

## What to figure out together before the first real run

NFL isn't a drop-in replacement for MLB's data shape, so let's nail these down first:
- **Data source(s)**: what API or site will feed schedule/scores/stats/injuries? (MLB used the official MLB Stats API directly — NFL's equivalent might be ESPN's API, a stats provider, or scraping official team injury reports — tell me what you have access to or want me to find.)
- **What "rolling stats" means for a 17-game season**: MLB used a trailing 15-games/21-days window; NFL's short season probably wants something like "last 3-4 games" or "current season only," not a long rolling window. Your call.
- **What replaces "bullpen ERA"**: some team-defense stat that matters for your betting angle — points allowed, sacks, turnover margin, whatever you actually use to make picks.
- **Odds format**: spread + total + moneyline is the baseline; tell me if you also want first-half lines (NFL's analog to MLB's "first 5 innings" markets) or player props.
- **Bye weeks**: build.py needs to just skip teams on a bye that week, not error or show stale data for them.
